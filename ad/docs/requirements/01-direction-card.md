## 二、行业理解

广告制作公司（也常叫"图文快印店""广告物料供应商"）为其他企业客户制作线下和线上的宣传物料。

**典型产品**：海报、展架、菜单、宣传册、DM 单、公众号配图、门头招牌等。

**核心业务逻辑**：
```
接单 → 拆分成具体物料任务 → 设计制作 → 客户确认 → 交付
```

**行业竞争点**：不仅在设计质量，还在交付时效和沟通效率。客户的需求往往是"给我做一套开业用的东西"，需要广告公司把模糊的创意要求转化为按时、按规格交付的实体或数字物料。

---

## 三、业务问题（痛点）

一句话：**"上传了文件"、"客户确认了文件"、"整笔订单完成"是三件不同的事，但现在被混成了一件。**

具体表现：

| # | 场景 | 问题 |
| --- | --- | --- |
| 1 | 客户经理在微信上接了需求 | 设计人员只看到一句"做得年轻一点"，不知道尺寸、数量、用途 |
| 2 | 设计稿改了两次 | 没人说得清客户最终确认的是哪一版，线上传了文件 ≠ 客户点头了 |
| 3 | 周五要交付 | 海报做好了但展架没完成，客户经理只能逐个人问进度 |
| 4 | 已经交付的订单 | 客户临时加一张展架或改尺寸，变更过程没有记录，说不清谁确认了什么 |

---

## 四、主要岗位

| 角色 | 在这个系统里做什么 | 关键动作 |
| --- | --- | --- |
| **客户经理** CS_MANAGER | 登记客户和物料要求、上传参考资料、记录客户修改意见、记录客户最终确认、发起交付 | 登记客户、创建订单、记录客户确认结果 |
| **业务负责人** BIZ_LEADER | 审核订单物料清单、确认截止时间、把海报/展架等任务分派给设计人员、检查延期 | 确认订单范围、分派人员、检查延期情况 |
| **设计制作人员** DESIGNER | 接收分派给自己的物料任务、上传设计稿初稿、根据修改意见提交新版本、查看截止时间 | 接收海报/展架等任务，上传设计稿并根据意见修改 |

> **首版不涉及**：印刷/生产岗、仓库/配送岗、财务岗。后续扩展时考虑。

## 五、初步链路

```
客户经理接到客户需求
       │
       ▼
 【创建订单】  填写客户信息、物料清单（类型/尺寸/数量/用途）、整体截止时间、参考说明
       │
       ▼
 【负责人确认】  审核物料清单是否合理、截止时间是否可行
       │
       ▼
 【任务分派】  负责人把每项物料分别派给具体的设计制作人员
       │
       ▼
 【设计人员上传初稿】  设计人员上传设计稿文件，系统记录版本号 v1
       │
       ▼
 【客户经理反馈客户意见】  客户看了初稿 → 客户经理录入"客户修改意见"
       │
       ▼
 【设计人员提交新版本】  上传 v2，旧版本 v1 保留可查看
       │
       ▼
 【客户经理记录客户确认】  客户说"可以了" → 标记某项物料为"已确认"
       │
       ▼
 【订单完成判断】  只有订单内全部物料都标记"已确认"，整笔订单才变为"已完成"
```

### 主状态流转

```
DRAFT → CONFIRMED → IN_PROGRESS → PENDING_DELIVERY → COMPLETED
                                              ↑
                                    任一物料未确认 → 继续"制作中"
```

### 物料任务状态

```
待分派 → 已分派 → 制作中 → 待客户确认（初稿上传后）
                              ↓
                              退回修改（客户有意见）
                              ↓
                              已修改（有新版本）
                              ↓
                              待客户确认（再次上传后）
                              ↓
                              已确认（客户点头）
```

## 七、选择原因

1. **场景具体，容易具象化**。奶茶店开业要海报和展架——这个场景所有人都见过，不需要理解复杂的行业概念就能代入。

2. **业务边界清晰**。任务书明确说"不做 ERP、不接支付、不做在线图片编辑"，避免了越做越大的"需求膨胀"，适合 MVP 闭环。

3. **能完整体现"岗位协作 + 状态流转 + 版本留痕"**。客户经理、负责人、设计人员三个角色各有明确的事情，订单和物料都有状态流转，版本管理是这个行业特有的需求——这些都能覆盖课程要考的"企业业务系统共同交付底线"。

4. **行业认识有价值**。通过这个项目能理解"上传了文件"、"客户确认了文件"、"整笔订单完成"为什么是三件不同的事——这种认知在其他选题（退换货、快递异常、养老院照护）里也都存在，是通用的企业业务系统思维。

5. **有真实的行业痛点**。"聊天记录丢失、版本混乱、谁也说不清现在什么状态"这个问题在小公司里真实存在，做完这个项目能说清楚"为什么需要这种系统"，而不只是"学会了写代码"。
